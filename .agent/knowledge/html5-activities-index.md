# Reusable Deck-Local HTML5 Activities

Index of custom interactive widgets built directly inside a presentation's own
HTML/CSS/JS (vanilla, no external libraries). These are distinct from
ActiveBits-hosted "embedded activities" (see
`.agent/skills/vendor/syncdeck/references/AVAILABLE_ACTIVITIES.md`) — everything
here lives inline in the deck itself and is meant to be copied/adapted, not
launched.

When building a new interactive moment, check this list first. If an existing
engine fits the shape of the interaction (classify items, trace state
step-by-step, select-all-that-apply, timed random prompt, progressive reveal,
drag-to-correct-target), copy the relevant `init*` function and markup from the
source file and re-skin it with new content rather than inventing a new
mechanism.

## Generic, highly reusable engines

### Variable-box code trace
- **Where:** `Decks/HPy/Unit 1 - Basic Programming Constructs/1.2 - Data, Expressions, and Variables/1.2-data-expressions-and-variables.html` (`initVarBoxTrace`, JS ~1938-2115, HTML ~362-383)
- **Also reimplemented as:** `initCallTrace` in `.../1.3 - Functions/1.3-functions.html` (JS ~1793-1981); `initBranchTrace` in `.../1.4 - Conditionals/1.4-conditionals.html` (JS ~1737-1927)
- **Concept:** step through a code listing line-by-line (`done`/`current`/`pending` highlighting) while dragging value "chips" onto empty variable boxes to trace program state.
- **Mechanism:** native HTML5 drag-and-drop (`draggable`, `dragstart`/`dragover`/`drop`) with a click-to-select fallback for accessibility; a state object tracks the current step index and box values, with correct/incorrect feedback.
- **Reuse:** very generic — works for any procedural code sequence where you want learners to predict variable state at each step. Follows the `data-fragment-trace` code-tracing convention in AGENTS.md (current-line-is-next-to-execute).

### Chip-to-bin classifier
- **Where:** same file as above, `initTypeSort` (HTML ~775, JS ~2115+) — sorts values into data-type bins (int/float/str/bool)
- **Also reimplemented as:** `initTruthySort` in `1.3-functions.html` (truthy/falsy); `initBoolSort` in `1.4-conditionals.html` (boolean-expression sort)
- **Concept:** drag chips from a tray into labeled bins; a "N of M sorted" counter tracks progress and correctly-placed chips are removed from the tray.
- **Mechanism:** same drag/drop + click-fallback mechanism as the variable-box trace.
- **Reuse:** very generic classification pattern — swap bin labels and chip data for any "sort these into categories" exercise (data types, even/odd, parts of speech, etc.).

### Select-all-that-apply scenario matcher
- **Where:** `Decks/AR2/ShopSafety/Industrial_Warning_Signs.html`, `initChooseGame` (section ~595-616, JS ~877-990)
- **Concept:** present a scenario, learner multi-selects applicable chips from a bank, "Check Answer" marks each `state-correct`/`state-incorrect`/`state-missed` with a scored summary ("N of M correct, X missed, Y extra").
- **Mechanism:** pure click-based (no drag), `chosen` map tracks selection state, resets on `Reveal slidechanged`.
- **Reuse:** strong generic fit for any "select all that apply against a scenario" assessment.

### Staged progressive-reveal scenario
- **Where:** `Decks/AR2/ShopSafety/Making_Warnings_Unnecessary.html` — three instances of the same engine: `initBeyondGame` (~1324-1391, section `#beyond-game` ~661), `initPpeGame` (~1391-1466, `#ppe-game` ~835), `initRiskyGame` (~1466-1523, `#risky-game` ~962)
- **Concept:** a scenario description with a sequence of hidden "stage" panels; each button click reveals the next stage (marking prior ones `.done`) until all are shown, then advances to the next scenario.
- **Mechanism:** click-driven progressive reveal, per-scenario reset on slide change, no drag/drop.
- **Reuse:** generic step-by-step walkthrough pattern (hazard→control→limit, cause→effect chains, any staged reveal).

### Countdown timer with completion sound
- **Where:** `Decks/CSP/Cybersecurity/security-risks-part-1.html` (`makeCountdown`, JS ~334-415, two instances `t3`/`t4`); reused in `Decks/CSP/Unit 3 - Code.org - Intro to App Design/3.3 - Project_ Designing An App Part 1/3.3-project-designing-an-app-part-1.html` (two instances `t1`/`t2`, slides 4 and 7)
- **Concept:** a plain Start/Stop/Reset countdown clock (`MM:SS`) for a timed activity, e.g. group work or a Code.org step that carries its own suggested time. The display turns amber inside the last 30-60s and red at zero, and a `times-up.mp3` chime plays once when the clock hits zero.
- **Mechanism:** `makeCountdown(id, totalSecs)` takes an id prefix (`#<id>-display`, `#<id>-start`, `#<id>-stop`, `#<id>-reset`) and a duration in seconds; plain `setInterval`/`clearInterval`, one shared `new Audio('times-up.mp3')` instance per deck. No Reveal fragment/slidechanged wiring — the clock just keeps running if you navigate away, matching how an instructor actually uses it (start it, then advance slides while it counts down in the background... though note it isn't visible again until you return to that slide). Requires a local `times-up.mp3` copied into the deck's own folder (each deck keeps its own copy rather than sharing one from the runtime).
- **Repeating variant with length toggle:** `makeRepeatingCountdown('switch-timer', 5*60)` in `afterInit` — same markup on the "Open Code.org" setup slide of `3.5 - Intro to Programming/3.5-intro-to-programming.html` (slide 8), `3.6 - Debugging/3.6-debugging.html` (slide 9), and `3.7 - Designing an App Part 3/3.7-designing-an-app-part-3.html` (slide 6), all under `Decks/CSP/Unit 3 - Code.org - Intro to App Design/`. It is the same display/`.warning`/`.expired`/chime engine with two changes: (1) on reaching zero it sets a `loopPending` flag instead of stopping, so the next tick holds `00:00` for one second then resets to the selected length and keeps ticking — a recurring "swap driver/navigator" nudge; (2) it reads `.timer-dur-btn[data-dur]` pills inside the `#<id>` wrap (here `5 min` / `10 min`) and, on click, stops-and-resets to that many seconds and moves the `.is-active` class. Duration pills are `disabled` while running. In 3.6 and 3.5 (which had no `afterInit` or `getLiveElementById` before) the helper is defined locally inside the added `afterInit`. While the chime is playing the `.timer-label` gets an `is-flashing` class driving a fast amber `steps()` blink (cleared on the audio's `ended` event, with a 3s safety timeout for the autoplay-blocked case, and on Stop/Reset/length-change via `stop()`); a `prefers-reduced-motion` block holds the label solid amber instead. Use this shape for any "every N minutes, do X" classroom loop where the instructor may want to pick between a couple of preset intervals.
- **Reuse:** the generic go-to for any Code.org-style lesson slide that carries a literal countdown-badge image in the source slides (e.g. a static "2:00" graphic) — replace the static image with this live widget set to the same duration. Multiple independent instances can coexist on different slides of the same deck (each gets its own id prefix passed to `makeCountdown`).

### Multi-base binary/decimal odometer
- **Where:** `Decks/CSP/Unit 1 - Digital Information/1.5 - Overflow and Rounding/1.5-overflow-and-rounding.html` (`#binary-odometer` section, `initBinaryOdometer`)
- **Concept:** an 8-bit value is displayed simultaneously as a row of binary bit tiles and a 3-digit decimal readout. Start/Stop buttons drive a `setInterval` counter, a speed slider controls the tick interval, and a value slider (0-255) jumps straight to any 8-bit value. Crossing 255 wraps to 0 and fires a flashing "Overflow!" banner.
- **Mechanism:** plain `setInterval`/`clearInterval` counter loop (same slidechanged-cleanup pattern as the Disruptus timer), a `render()` function that derives both the bit tiles and the decimal digits from one shared integer so the two bases never drift out of sync, and a CSS keyframe animation retriggered via an `offsetWidth` reflow trick for the overflow flash.
- **Reuse:** generalizes to any "watch a fixed-width counter wrap around" demonstration, swap the bit width/base pair (e.g. hex/decimal, a 4-bit nibble) by changing the `padStart` width and the number of bit tiles.

### Pushbutton/toggle state-chain stepper with animated transitions
- **Where:** `Decks/AR2/StateMachines/State_Machines_Intro.html` — two instances of the same markup pattern: `#sm-diagram-4` (4-state, ~slide 10) and `#sm-diagram` (8-state, moved to the closing capstone slide), each a chain of `.chain-node` circles and `data-arc="0"`..`"N"` SVG transitions, buttons, and an insight callout; both driven by one shared `initStateMachineDemo(Reveal, idSuffix, numStates)` JS in the trailing `<script>`.
- **Concept:** a horizontal chain of numbered state circles connected by curved SVG arcs (plus a return arc looping the last node back to the first), driven by a Start button and a Step button. When the buttons appear, the whole diagram dims except the next relevant trigger arc/label. Pressing the right button "draws" that arc's path from tail to arrowhead, then lights up the destination state and shifts the highlight to the following trigger, so exactly one state and one upcoming trigger are ever highlighted at a time.
- **Mechanism:** `path.getTotalLength()` + `stroke-dasharray`/`stroke-dashoffset` animated via a forced-reflow + CSS transition (the classic SVG "line draw" technique), with the arrowhead `<marker>` opacity held at 0 until the draw finishes so it doesn't appear to float ahead of the line; a `currentArc`/`DEST[]` lookup table drives a `chain-dimmed` container class plus `.active`/`.highlight` toggles on nodes and arcs. Demo state activates/deactivates via `Reveal.on('fragmentshown'/'fragmenthidden', ...)` scoped to the specific buttons fragment (not just `slidechanged`), so stepping backward past that fragment cleanly un-dims everything.
- **Parametrized for reuse within the same deck:** the function takes an `idSuffix` (so two instances can coexist on different slides without id collisions — `'-4'` vs `''`) and `numStates` (drives `DEST[]` generation and every loop bound that used to be hardcoded to the state count). The loop-back arc's cubic-Bézier path is recomputed per instance by keeping the same endpoint-to-control-point offset (±92,92, which is what actually produces the ~45° corner-touching tangent) rather than linearly scaling the original path string, so the geometry stays correct at any width.
- **Reuse:** the dasharray/dashoffset draw-in plus marker-delay trick generalizes to "animate any SVG path drawing itself" (wiring diagrams, flowcharts, causal chains); the dim-all-but-the-next-highlighted-element pattern generalizes to any guided step-through of a diagram; the `idSuffix`/count-parametrization approach generalizes to any deck that wants "the same interactive diagram at two different scales" without duplicating the JS.

### Interactive hotspots on a redrawn schematic symbol
- **Where:** `Decks/AR2/StateMachines/State_Machines_Intro.html` (`#rs-latch-demo` ~line 425, `initRsLatchDemo` JS in the trailing `<script>`)
- **Concept:** a real piece of other software's iconography — here, FluidSim's RS latch block symbol — is redrawn as a small inline SVG (box + two input wire stubs + one output wire stub), then gets small live controls (Set/Reset buttons, a Q output light) positioned exactly at the wire endpoints, plus short colored connector lines bridging each control to the drawing. Pressing Set lights the output; pressing Reset clears it.
- **Mechanism:** started from a screenshot of the real symbol; its pixel geometry (wire endpoint coordinates, box edges) was measured once with a throwaway PIL script, converted to fractions of the image's width/height, then rebuilt as an SVG `viewBox` sized to match those same fractions 1:1 — so the original overlay math (fixed-px `position:absolute` offsets for the buttons/light) kept working unchanged when the raster image was swapped for the vector redraw. The SVG itself uses `stroke="var(--text)"` rather than the deck's accent green, deliberately reading as neutral/monochrome so it looks like "real software output" rather than one of the deck's own color-coded pedagogical diagrams. No fragment-gating or animation; just click handlers toggling a `.on` class on a small indicator, reset on `Reveal.on('slidechanged', ...)`.
- **Reuse:** generalizes to recreating any simple external-software icon/symbol as a crisp, theme-colorable SVG and wiring interactive callouts to its connection points; the "measure a reference image once, rebuild as SVG at the same viewBox fractions" trick keeps overlay coordinates stable across that swap.
- **Simplified variant:** `#s1-latch-demo` (~line 570, `initS1LatchDemo`) reuses the same button/light/`.rs-light` mechanism for a *hand-drawn* (not traced-from-a-reference) box, so there's no separate raster image to align against. It sidesteps the earlier connector-bar alignment bug entirely: rather than a colored `<div>` connector bar positioned independently next to the SVG wire (two elements whose centers have to be hand-computed to match), the SVG wire's endpoint coordinate *is* the button/light's `left`/`top` anchor, so they're mathematically the same point rather than two numbers that have to be kept in sync by hand.

### Photo carousel stepping through real-world states, with optional live output badges
- **Where:** `Decks/AR2/StateMachines/State_Machines_Intro.html` — two instances of the same markup pattern: `#machine-carousel-intro` (~slide 30, photos only) and `#machine-carousel-test` (~slide 35, photos plus active-output badges), both driven by one shared `initMachineCarousel(Reveal, idSuffix)` JS in the trailing `<script>`.
- **Concept:** a single photo of a real physical machine (a pneumatic pick-and-place arm) with a state-label badge overlaid in the corner, a caption describing what's happening, and one button that always shows whichever trigger fires next (`Start` the first press, then `Step`/`~Step` alternating). Clicking the button advances through the machine's real states in order and loops back to the first rather than returning to an idle "Ready" pose, mirroring the Start/Step/~Step arc labels used on the deck's abstract state-chain diagrams. The `test` instance additionally renders a row of colored badges (`Q# · solenoid · action`, e.g. `Q3 · 2M2 · UP`) under the caption for whichever outputs are active in that state, or "No outputs active" when none are.
- **Mechanism:** state data is a plain array of `{src, alt, caption, outputs}` objects plus a separate `READY` object for the pre-Start pose; an `index = -1` sentinel represents Ready, and `index = (index + 1) % STATES.length` on each click naturally produces "Ready once, then loop forever" without special-casing the wraparound. `outputs` is an array of `{q, name}` pairs rendered into an optional `#machine-carousel-outputs-<idSuffix>` element that the function no-ops around if the slide doesn't have one (so the same state table drives both a bare photo carousel and one with live output readouts). Resets to Ready on `Reveal.on('slidechanged', ...)`.
- **Parametrized for reuse within the same deck:** the function takes an `idSuffix` so multiple carousels can coexist on different slides without id collisions, following the same pattern as `initStateMachineDemo`'s `idSuffix`/`numStates` parametrization above — every element lookup and the root `#machine-carousel-<idSuffix>` selector are suffixed, so adding a third instance is just another HTML block plus another `initMachineCarousel(Reveal, 'newSuffix')` call.
- **Reuse:** generalizes to any "step through real-world photos of a system in different states" demo, with or without a secondary live-readout row (outputs, sensor values, counters) keyed off the same state index.

### Draggable node-graph builder ("Draw It" network activity)
- **Where:** `Decks/CSP/Unit 2 - The Internet/2.2 - Building a Network/2.2-building-a-network.html` (`.netbuild` markup, four instances `#netbuild-1`..`#netbuild-4` on slides 5/7/9/11; `initNetworkBuilder` JS inside `afterInit`)
- **Concept:** a small set of labeled SVG nodes arranged on a circle; students drag from one node to another to add a connection (a slightly bowed quadratic-bezier curve rather than a straight chord, so overlapping connections stay visually distinguishable), and click an existing line to remove just that one. Dragging the same pair again adds a second, redundant parallel line instead of removing the first — parallel lines between the same pair fan out sideways so multiple backup connections stay individually visible and clickable rather than stacking exactly on top of each other. A stats bar tracks total connection count and whole-graph connectivity. Two optional tools escalate with the lesson's guidelines: "Test a Cut" lets a student click one strand of a connection to simulate severing just that physical line (a redundant pair survives a single cut) and flags any node that becomes fully unreachable in red; "Find a Path" lets a student tap two nodes to highlight the shortest remaining route between them and reports the hop count.
- **Mechanism:** node positions are computed from a labels array on a circle (`cx + r*cos/sin`), not hardcoded, so the node count is parametrizable. Edges are stored as a per-pair *count* (`edges["A-B"] = 2`) rather than a boolean, with a parallel per-pair cut *count* (`cuts["A-B"]`) capped at the edge count; connectivity BFS treats a pair as traversable only while `edges[k] - cuts[k] > 0`. Rendering draws `count` separate paths per pair, each offset sideways from the shared outward bow by `(index - (count-1)/2) * spread` so 1, 2, or 3 parallel strands read as distinct fanned lines instead of one thick overlap; clicking a specific rendered strand reads *that strand's own* cut/active state (by its render index against the pair's cut count) to decide whether the click cuts one more or restores one, so the interaction reads as "click a red strand to restore it, click a live strand to cut it" even though strands aren't independently tracked once cut/uncut. Dragging is implemented with plain `pointerdown`/`pointermove`/`pointerup` listeners on the SVG root — deliberately *not* `setPointerCapture` — because capturing the pointer caused Chromium to occasionally fire a spurious `pointercancel` when a new drag started from the node that had just been the previous drag's drop target; listening on `window` for move/up sidesteps that capture-lifecycle quirk. A single pointer gesture does double duty: dragging fully from node A to node B commits an edge directly, while a plain tap (down+up on the same node with no distinct second node) arms it as a "selected" node so a following tap on a second node connects them too — giving touch/keyboard users a click-click fallback without a separate code path. Each of the widget's DOM lookups goes through a `getLiveElementById` helper (`querySelectorAll('#id')` filtered to exclude anything under `#storyboard`) since SyncDeck's storyboard strip clones slide markup including duplicate ids, so a plain `document.getElementById` risks returning the inert clone. **Bug worth remembering:** conditionally toggling a class via `classList.toggle(name, someExpression)` is only safe if `someExpression` is coerced to a real boolean first (`!!(...)`) — passing a value that evaluates to `undefined` (e.g. an `&&` chain that starts with a falsy-but-not-boolean guard) makes `classList.toggle` perform a genuine toggle instead of forcing the state, which desyncs the visual state from the data model on every re-render.
- **Reuse:** the node-on-a-circle + drag-to-add/click-to-remove mechanism generalizes to any "build a graph" activity (network topology, state-machine wiring, relationship mapping); the count-per-pair model generalizes to any activity that wants to teach redundancy through literal parallel/backup connections rather than just presence-or-absence edges; the cut-simulation and shortest-path tools generalize to any lesson that wants students to reason about redundancy or path length over a graph they built themselves, not a pre-made one.
- **Also worth remembering:** resonance/postboard question `text` is the *only* thing students see once the activity overlay launches — the surrounding slide's prose (background context, setup) is hidden behind it. Any context the question depends on (e.g. "recall X from last lesson...") has to be restated inline in the question `text` itself, not left to the slide's own paragraph.

### Click-to-select mixed-grid matching pairs
- **Where:** `Decks/CSP/Unit 2 - The Internet/2.4 - Routers and Redundancy/2.4-routers-and-redundancy.html` (`#match-vocab` section ~slide 12, `initMatchingPairs` JS in `afterInit`); also `Decks/CSP/Unit 2 - The Internet/2.5 - Packets/2.5-packets.html` (`#match-vocab` section ~slide 20, same JS shape with a 5-pair set)
- **Concept:** N vocabulary terms and their N definitions (2N cards total) are dealt onto a single shuffled 4-column board — terms and definitions sit side by side in no particular order, mirroring a physical "mixed card" matching exercise rather than two separate label/definition lists. Clicking any two cards attempts a match; a correct pair locks both cards into a disabled "matched" state (green) and increments a "N of M matched" counter, while an incorrect pair shakes both cards red for 400ms and clears the selection. An attempts counter tracks every pairing try (right or wrong), and a "Nicely done!" inline message appears once every pair is matched. On top of that, a full-slide `.match-perfect-overlay` (absolutely positioned sibling of `.slide-inner`, matching the `.glow` decorative-div pattern so it scales correctly with Reveal's canvas) flashes a large animated checkmark and "Perfect Match!" banner once `matched === MATCH_PAIRS.length` — sized to be readable from across a classroom, not just on-screen — and is click-to-dismiss (removes the `.visible` class without resetting match state) so the instructor can still see the solved board underneath.
- **Mechanism:** each `{id, term, def}` pair is exploded into two flat `{id, label, isTerm}` tiles, then the full tile array is shuffled together with a Fisher-Yates `shuffled()` helper and rendered from scratch (fresh shuffle, fresh state) every time `Reveal.on('slidechanged', ...)` reports the student has (re)entered that specific section — so replaying the activity always produces a new board layout rather than the solved one. Matching itself is pure click state (a single `selected` variable, not two column-scoped ones), not drag-and-drop, so it needs no dragstart/dragover wiring and works identically with mouse, touch, or switch-access. Term tiles get a bold monospace treatment (`.match-card-term`) purely as a subtle visual hint; nothing about the click logic depends on that distinction, since two same-`id` tiles are guaranteed to be one term and one definition. The overlay element is looked up once via `root.closest('section').querySelector('[data-match-overlay]')` (root itself already resolved through the repo's `getLiveElementById` convention filtering out the SyncDeck storyboard's cloned copy), and `updateStatus()` toggles its `.visible` class alongside the existing inline complete-message logic — so the overlay auto-hides again on the next fresh shuffle without any extra reset code.
- **Reuse:** the most generic "N terms vs. N definitions/images/examples, presented as one shuffled board" matching mechanism in the repo — swap the `{id, term, def}` array for any two-sided pairing exercise (vocabulary, formula-to-name, cause-to-effect, code-snippet-to-output) without touching the click/shuffle/scoring logic. If a two-column (all-terms-on-the-left, all-definitions-on-the-right) layout is wanted instead, split the render step back into two `shuffled()` calls against separate host elements — the click/match/score logic underneath doesn't care which DOM layout the tiles land in. Prefer this over the drag-based credential matcher below when the pairing itself (not physical placement) is the point, and ActiveBits has no native "matching pairs" activity type to reach for instead. The perfect-score overlay pattern itself (big animated banner absolutely positioned as a `.slide-inner` sibling, toggled from whatever scoring function already tracks completion, click-to-dismiss) generalizes to any single-slide activity that wants a from-across-the-room "you nailed it" moment — not just matching.

### Drag-and-drop fill-in-the-blank with word bank
- **Where:** `Decks/CSP/Unit 2 - The Internet/2.6 - HTTP and DNS/2.6-http-and-dns.html` (`#fillblank-dns` section ~slide 6, `initFillBlank` JS in `afterInit`)
- **Concept:** a sentence is rendered with inline `.blank` drop-zones in place of missing words (here, the DNS definition: "The ___ ___ ___, or DNS, is a network of ___ that track the ___ of different domain names like ___."), with a shuffled word bank of chips below it — one chip per blank, no distractors. Dragging (or click-selecting, then click-placing) a chip onto its correct blank locks it in green inline; a wrong blank shakes red and the chip stays in the bank for another try. Shares the exact "N of M filled / N attempts / perfect-run overlay + pulsing badge" status-and-reward plumbing as the matching-pairs activity above, including the same "perfect means zero wrong attempts, not just eventual completion" definition (`attempts === blank count`).
- **Mechanism:** native HTML5 drag-and-drop (`draggable`, `dragstart`/`dragover`/`drop` with `DataTransfer`) is the primary interaction, with a parallel click-to-select-then-click-to-place path sharing the same `placeWord(word, chipEl, blankEl)` correctness check, so both input modes produce identical state and both count toward the same attempts/perfect logic — no separate code path to keep in sync. Blanks are plain inline `<span data-blank-answer="...">` elements sized with `min-width` so the sentence keeps its shape empty or full; a correct drop sets the blank's text and a `.blank-filled` class, a wrong drop only flashes `.blank-wrong` and leaves the blank empty so the same chip (or a different one) can be retried. Used chips fade out via `.chip-used` (opacity/scale) rather than being removed from the DOM, keeping bank layout stable. Full reshuffle-and-reset happens on `Reveal.on('slidechanged', ...)` re-entry, identical to the matching-pairs reset pattern.
- **Reuse:** generalizes to any "N blanks, N-word bank, exactly one correct placement each" fill-in-the-blank exercise (vocabulary sentences, labeling a diagram with a word list, ordering-by-fill steps) — swap the sentence markup and the `WORDS` array. If some blanks should accept multiple valid words or the bank should carry distractors, the correctness check (`blankEl.dataset.blankAnswer === word`) would need to become a set-membership test instead of exact match, but the drag/click/scoring scaffolding stays the same.

### Fragment-triggered frame-swap stage
- **Where:** `Decks/CSP/Unit 2 - The Internet/2.6 - HTTP and DNS/2.6-http-and-dns.html` — two instances of the same `initFrameSwap(containerId, onFrame)` helper in `afterInit`: `#fragtour-shot` (~slide 14, a single annotated screenshot with four `.shot-highlight` callout boxes cycling across Server / DNS Lookup Table / Source HTML / Rendered View, plus a caption line swapped via the `onFrame` callback) and `#flipbook-layers` (~slide 24, an 11-frame comic-strip flip-book of a message being encapsulated down the network stack, crossing the wire, and decapsulated back up to deliver a punchline)
- **Concept:** a stack of `position:absolute` "frames" (screenshots, highlight boxes, or comic panels) occupies the same box, and only one frame is visible (`.frame-active`) at a time; clicking through advances to the next frame like a flip-book or a guided tour of one image, and clicking back reverses it. Both current uses in this deck are purely illustrative walkthroughs (no scoring), resetting to frame 0 whenever the slide is re-entered.
- **Mechanism:** deliberately does *not* rely on Reveal's own fragment `.visible` opacity (the deck's base CSS forces that to a blunt 0/1 toggle via `!important`, which can't express "only the current one is ever shown"). Instead, invisible zero-size `<span class="fragment frame-trigger">` elements exist purely to be Reveal fragment steps; `initFrameSwap` listens for `Reveal.on('fragmentshown'/'fragmenthidden', ...)` and compares `e.fragment` against its own resolved trigger elements (found via the section, already filtered through the storyboard-safe root lookup) to decide which real frame gets `.frame-active`. An optional `onFrame(idx, trigger)` callback lets a caller react to each step beyond just showing the frame — the callout-tour instance uses it to swap a caption paragraph's text from each trigger's `data-frame-caption` attribute. This is the same "rAF-adjacent, event-synced class toggle" family as the older fragment-synced diagram morph technique in the AR1 deck, generalized into a reusable two-argument helper instead of a one-off inline handler.
- **Reuse:** the most generic "step through N stacked visuals, one at a time, driven by Reveal's fragment/keyboard/click navigation" engine in the repo — reuse directly for any annotated-screenshot tour (swap which region of one image is highlighted), comic-strip or storyboard-style sequential narrative, or before/after image series, by supplying a `container` with `.swap-frame[data-frame="N"]` elements plus `N` matching `.frame-trigger` fragments and calling `initFrameSwap('containerId')`. Add an `onFrame` callback only when something besides frame visibility (captions, badges, audio cues) needs to change in lockstep.

### Commit-then-check two-bin classifier with perfect overlay
- **Where:** `Decks/CSP/Unit 3 - Code.org - Intro to App Design/3.2 - Introduction to Design Mode/3.2-introduction-to-design-mode.html` (`#classify-io` section ~slide 8, `initClassifyIO` JS in the trailing `<script>`)
- **Concept:** twelve chips start in an unsorted tray above two labeled bins (here, Input/Output). Students freely drag (or click-select, click-place) chips between the tray and either bin with no correctness feedback at all — unlike the instant-feedback chip-to-bin classifier below, a chip can sit in the "wrong" bin indefinitely. A "Check My Answers" button stays disabled until the tray is empty (all chips placed), then locks the whole board (chips lose `draggable` and clicks become no-ops), marks every chip green/red with a ✓/✗ badge, and updates a score badge to "N of 12 correct." A perfect score triggers the same full-slide click-to-dismiss "Perfect!" overlay used by the matching-pairs activities elsewhere in the course; anything less than perfect swaps the Check button for a "Try Again" button that clears every placement back to the tray and unlocks the board for a fresh attempt.
- **Mechanism:** a single `state.placement` map keyed by item id holds `'tray'|'input'|'output'` (no separate boolean-per-item bookkeeping), so moving a chip is just overwriting one map entry and re-rendering all three containers from scratch. `state.locked` gates every interaction handler (drag, click, keydown) so the board becomes inert the instant Check is pressed, and `render()` only injects the ✓/✗ mark and correct/incorrect class when `state.locked` is true, keeping the correct-answer data invisible in the DOM until after commit. Drag (`dragstart`/`dragover`/`drop`) and click-to-select-then-click-to-place share the exact same `place(itemId, bin)` call, identical to the fill-in-the-blank activity's dual-input-path pattern. Follows the repo's `getLiveElementById` convention (filtering out the storyboard's cloned copy) and resets fully on `Reveal.on('slidechanged', ...)` re-entry.
- **Reuse:** the most generic "sort N items into two labeled bins, but don't reveal right/wrong until an explicit commit" mechanism in the repo — swap the `CLASSIFY_ITEMS` array (`{id, label, correct}`) and the two bin labels for any binary classification exercise (true/false, before/after, category-A/category-B) where instant per-drop feedback would give away the answer prematurely. Extending to more than two bins just means adding more `data-bin` containers and `classify-bin-header` variants; the `state.placement` map and `place()` function don't assume exactly two destinations. Prefer the instant-feedback chip-to-bin classifier (above, in "Generic, highly reusable engines") when immediate right/wrong feedback per drop is pedagogically desirable instead.

### Drag-to-correct-target credential/tool matching
- **Where:** `Decks/CSP/Cybersecurity/public-private-key-lab.html` (cards ~500-1050, staged wiring/validation ~1280-1433); adapted again in `Decks/CSP/Cybersecurity/protecting-data.html` (cards ~710-1050, wiring ~1950-2059)
- **Concept:** draggable `.key-card` elements (public/private keys) dropped onto `[data-drop-zone]` targets across multiple staged slides (`data-crypto-lab="encrypt"|"decrypt"|"signature"|"tamper"|...`), validating whether the correct key was used, plus a tamper-detection text input.

- **Reuse:** content (asymmetric encryption) is specific, but the drag-a-labeled-card-onto-a-labeled-slot-with-correctness-validation mechanism generalizes to any "which credential/tool goes where" simulation.

### Fragment-synced diagram morph
- **Where:** `Decks/AR1/DCCircuits/EX7_Parallel_and_Mixed_Circuits.html` (JS ~1994-2110)
- **Concept:** as Reveal fragments advance/reverse across several slides, a parallel-branch circuit diagram visually collapses into its series equivalent (and expands back) in sync with fragment navigation.
- **Mechanism:** toggles a `.collapsing` class deferred via `requestAnimationFrame` to guarantee the CSS transition starts from the correct state, avoiding a transition/reflow race condition.
- **Reuse:** diagram-specific, but the "rAF-deferred class toggle synced to fragment events" technique generalizes to any before/after visual transformation tied to slide progression (equivalent circuits, chemical reactions, state diagrams, etc.).
