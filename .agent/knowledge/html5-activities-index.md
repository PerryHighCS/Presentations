# Reusable Deck-Local HTML5 Activities

Index of custom interactive widgets built directly inside a presentation's own
HTML/CSS/JS (vanilla, no external libraries). These are distinct from
ActiveBits-hosted "embedded activities" (see
`.agent/skills/vendor/syncdeck/references/AVAILABLE_ACTIVITIES.md`) — everything
here lives inline in the deck itself and is meant to be copied/adapted, not
launched.

When building a new interactive moment, check this list first. If an existing
engine fits the shape of the interaction (classify items, trace state
step-by-step, select-all-that-apply, timed random prompt, progressive reveal,
drag-to-correct-target), copy the relevant `init*` function and markup from the
source file and re-skin it with new content rather than inventing a new
mechanism.

## Generic, highly reusable engines

### Variable-box code trace
- **Where:** `Decks/HPy/Unit 1 - Basic Programming Constructs/1.2 - Data, Expressions, and Variables/1.2-data-expressions-and-variables.html` (`initVarBoxTrace`, JS ~1938-2115, HTML ~362-383)
- **Also reimplemented as:** `initCallTrace` in `.../1.3 - Functions/1.3-functions.html` (JS ~1793-1981); `initBranchTrace` in `.../1.4 - Conditionals/1.4-conditionals.html` (JS ~1737-1927)
- **Concept:** step through a code listing line-by-line (`done`/`current`/`pending` highlighting) while dragging value "chips" onto empty variable boxes to trace program state.
- **Mechanism:** native HTML5 drag-and-drop (`draggable`, `dragstart`/`dragover`/`drop`) with a click-to-select fallback for accessibility; a state object tracks the current step index and box values, with correct/incorrect feedback.
- **Reuse:** very generic — works for any procedural code sequence where you want learners to predict variable state at each step. Follows the `data-fragment-trace` code-tracing convention in `.agent/knowledge/code-tracing.md` (current-line-is-next-to-execute).

### Data-driven memory trace board (TraceLift whiteboard mirror)
- **Where:** `Decks/CSP/Unit 4 - Variables, Conditionals, and Functions/4.1 - Variables Explore/4.1-variables-explore.html` (`TRACES` object + builder IIFE in the trailing `<script>`; ~25 `section[data-trace-board="key"]` slides)
- **Concept:** an instructor-paced, read-only trace that mirrors the pairs' whiteboard: numbered Program listing (with TraceLift `[[name]]` flaps that "lift" to show the substituted value), a Memory Trace with one box per function call (crossed out with an X and a FINISHED pill when the call returns) and per-variable columns whose older values are struck through, a Console, and a one-line narration panel per step. `data-trace-exercise` slides swap a "trace this with your partner" prompt for a "let's check" prompt once the first step is shown, so the empty board doubles as the exercise display and the answer key stays hidden until stepped.
- **Mechanism:** each trace is authored as a compact JS step list (`line`, `call`, `open`, `decl`, `set`, `close`, `out`, `lift`, `work`) instead of hand-placed fragments. Before `initSyncDeckReveal` runs, the builder renders the board DOM and appends one hidden `.fragment.trace-step` per step, so Reveal, the storyboard clone, and host sync all see ordinary fragments. On `fragmentshown`/`fragmenthidden`/`slidechanged`/`ready` every live board recomputes its state by folding steps `0..k` (k = visible step fragments), so back-navigation and jumps need no bookkeeping. A tiny tokenizer highlights the JS subset (and is reused for any static `[data-hl]` code block). Follows the current-line-is-next-to-execute convention in `.agent/knowledge/code-tracing.md`: effects land on the step that moves the caret past a line; a step that stays on the same line is the look-up/substitute/evaluate work.
- **List magnet variant (CSP Unit 6):** shared engine `Decks/CSP/Unit 6 - Lists, Loops, and Traversals/lists-magnet.js` and styles `lists-magnet.css`, used by every Unit 6 deck (`ListMagnet.prepare(TRACES)` before `initSyncDeckReveal`, `ListMagnet.attach(Reveal)` in `afterInit`). Each list is drawn as the class's 7-cell dry-erase magnet (red frame, cells over a 0 to 6 index row, cells past the length shaded) in a full-width Memory Trace under the program, with plain variables as Unit 4 columns beside it. Steps add `list: {name: [...]}` (the list's full contents after the step; cells that differ from the previous step highlight yellow) and `read: {name: [indexes]}` (cells being looked up highlight blue, including an empty cell past the end for an `undefined` read), and `sideW` narrows the narration column for long lines. List accesses never get flaps, matching the TraceLift sheets (a plain index variable on a sheet would be written `tops[ [[index]] ]`). `<div data-magnet="name" data-values='[...]'>` renders a static magnet on any slide. Examples: 6.1 (creating, accessing, insert/remove shifts), 6.2 (a computer lesson: `ListMagnet.prepare(TRACES, { plain: true })` draws each list at its real length in deck colors, with no magnet frame, and a dashed ghost cell for an index read past the end; random index and wrap-around index; a three-suspect bug hunt built on it is saved in `.agent/plans/csp-6.2-bug-hunt.md`).
- **Reuse:** the go-to for any JavaScript/App Lab tracing demo with variables and function calls (parameters vs. caller variables, copy-not-connect, per-call storage). Port to Python by swapping `KEYWORDS`/the token regex; extend for loops by revisiting lines (already supported: a step may set `line` back to an earlier line, and `lift: {n: []}` re-closes that line's flaps).

### Python list memory trace board (boxes, arrows, frames, candy trays)
- **Where:** shared by every deck in `Decks/HPy/Unit 4 - Lists/`: engine in `lists-unit.js` (`ListsUnit.prepare(LIST_TRACES)` before `initSyncDeckReveal`, `ListsUnit.attach(Reveal)` in `afterInit`), styles in `lists-unit.css` (`.lt-*`). Each deck authors its traces in a `LIST_TRACES` object and places `<div class="lt-board" data-trace="key">` on a slide. Examples: aliases and copies (4.4 slides 4, 8, 12, 16), a candy tray with index shifting (4.3 slide 7), the skipped-red removal bug (4.6 slide 7), a function call with copy and alias (4.10 slide 5).
- **Concept:** an instructor-paced, Python Tutor style trace: a highlighted code listing, a memory SVG with frames, variable boxes, arrows to list objects drawn as indexed cells, an optional loop-index pointer under a cell (red when past the end), a console, and one narration line per step.
- **Mechanism:** each step is a small diff (`line`, `frames`, `objs`, `candy`, `hl`, `ptr`, `print`, `err`, `say`) folded left to right, so back-navigation needs no bookkeeping. The builder appends one hidden `.fragment.lt-step` per step and lays out the SVG once across all steps (frame, variable, and object rows by first appearance; cell widths by their widest value), so nothing moves as steps advance. `layout` picks side-by-side, `'wide'` (memory full width below), or `'three'` (tall code, memory and console side by side). The same file also highlights any `<code class="py">` block. Follows the current-line-is-next-to-execute convention in `.agent/knowledge/code-tracing.md`.
- **Reuse:** any Python trace where references matter: aliasing, parameters, mutation versus reassignment, removing inside loops. `candy: {obj: true}` draws cells as colored candies for physical-model decks. `.agent/tools/trace_steps.py` screenshots individual steps.
- **Extras in the same engine:** a `.code-card[data-tutor]` gets a Python Tutor icon link built from its own code (`data-tutor-setup` / `data-tutor-after` add lines before or after, joined with `|`), and a call to any function whose `def` with a docstring is on the same slide gets a VS Code style hover showing its signature and docstring (a def in the same card wins, so two cards can define the same name). The highlighter carries triple-quoted strings across lines.

### Staged progressive-reveal scenario
- **Where:** `Decks/AR2/ShopSafety/Making_Warnings_Unnecessary.html` — three instances of the same engine: `initBeyondGame` (~1324-1391, section `#beyond-game` ~661), `initPpeGame` (~1391-1466, `#ppe-game` ~835), `initRiskyGame` (~1466-1523, `#risky-game` ~962)

- **Mechanism:** click-driven progressive reveal, per-scenario reset on slide change, no drag/drop.

- **Reuse:** generic step-by-step walkthrough pattern (hazard→control→limit, cause→effect chains, any staged reveal).

### Countdown timer with completion sound
- **Where:** `Decks/CSP/Cybersecurity/security-risks-part-1.html` (`makeCountdown`, JS ~334-415, two instances `t3`/`t4`); reused in `Decks/CSP/Unit 3 - Code.org - Intro to App Design/3.3 - Project_ Designing An App Part 1/3.3-project-designing-an-app-part-1.html` (two instances `t1`/`t2`, slides 4 and 7)
- **Concept:** a plain Start/Stop/Reset countdown clock (`MM:SS`) for a timed activity, e.g. group work or a Code.org step that carries its own suggested time. The display turns amber inside the last 30-60s and red at zero, and a `times-up.mp3` chime plays once when the clock hits zero.
- **Mechanism:** `makeCountdown(id, totalSecs)` takes an id prefix (`#<id>-display`, `#<id>-start`, `#<id>-stop`, `#<id>-reset`) and a duration in seconds; plain `setInterval`/`clearInterval`, one shared `new Audio('times-up.mp3')` instance per deck. No Reveal fragment/slidechanged wiring — the clock just keeps running if you navigate away, matching how an instructor actually uses it (start it, then advance slides while it counts down in the background... though note it isn't visible again until you return to that slide). Requires a local `times-up.mp3` copied into the deck's own folder (each deck keeps its own copy rather than sharing one from the runtime).
- **Repeating variant with length toggle:** `makeRepeatingCountdown('switch-timer', 5*60)` in `afterInit` — same markup on the "Open Code.org" setup slide of `3.5 - Intro to Programming/3.5-intro-to-programming.html` (slide 8), `3.6 - Debugging/3.6-debugging.html` (slide 9), `3.7 - Designing an App Part 3/3.7-designing-an-app-part-3.html` (slide 6), `3.7a - Designing an App Part 4/3.7a-designing-an-app-part-4.html` (slide 7), `3.7b - Designing an App Part 5/3.7b-designing-an-app-part-5.html` (slide 3), `3.8 - Using Simple Commands/3.8-using-simple-commands.html` (slide 9), and `3.9 - Creating Functions/3.9-creating-functions.html` (slide 6) — the last two use three pills `3 min` / `5 min` / `10 min`, default `3*60` — all under `Decks/CSP/Unit 3 - Code.org - Intro to App Design/`. It is the same display/`.warning`/`.expired`/chime engine with two changes: (1) on reaching zero it sets a `loopPending` flag instead of stopping, so the next tick holds `00:00` for one second then resets to the selected length and keeps ticking — a recurring "swap driver/navigator" nudge; (2) it reads `.timer-dur-btn[data-dur]` pills inside the `#<id>` wrap (`5 min` / `10 min`, or a third `3 min` pill in 3.8) and, on click, stops-and-resets to that many seconds and moves the `.is-active` class. Duration pills are `disabled` while running. In 3.6 and 3.5 (which had no `afterInit` or `getLiveElementById` before) the helper is defined locally inside the added `afterInit`. While the chime is playing the `.timer-label` gets an `is-flashing` class driving a fast amber `steps()` blink (cleared on the audio's `ended` event, with a 3s safety timeout for the autoplay-blocked case, and on Stop/Reset/length-change via `stop()`); a `prefers-reduced-motion` block holds the label solid amber instead. Use this shape for any "every N minutes, do X" classroom loop where the instructor may want to pick between a couple of preset intervals.
- **Also used in:** `Decks/AR1/Fluid Power/2 - Pushing_on_Fluids.html` slide 10 (`makeRepeatingCountdown('rotate-timer', 8*60)`, 6/8/10 min pills) as a lab station-rotation timer. Its CSS is in the Fluid Power unit `theme.css` (section 6) with every control at the 22px label floor, and the deck folder keeps its own `times-up.mp3`.
- **Reuse:** the generic go-to for any Code.org-style lesson slide that carries a literal countdown-badge image in the source slides (e.g. a static "2:00" graphic) — replace the static image with this live widget set to the same duration. Multiple independent instances can coexist on different slides of the same deck (each gets its own id prefix passed to `makeCountdown`).

### Multi-base binary/decimal odometer
- **Where:** `Decks/CSP/Unit 1 - Digital Information/1.5 - Overflow and Rounding/1.5-overflow-and-rounding.html` (`#binary-odometer` section, `initBinaryOdometer`)
- **Concept:** an 8-bit value is displayed simultaneously as a row of binary bit tiles and a 3-digit decimal readout. Start/Stop buttons drive a `setInterval` counter, a speed slider controls the tick interval, and a value slider (0-255) jumps straight to any 8-bit value. ### Pushbutton/toggle state-chain stepper with animated transitions
- **Where:** `Decks/AR2/StateMachines/State_Machines_Intro.html` — two instances of the same markup pattern: `#sm-diagram-4` (4-state, ~slide 10) and `#sm-diagram` (8-state, moved to the closing capstone slide), each a chain of `.chain-node` circles and `data-arc="0"`..`"N"` SVG transitions, buttons, and an insight callout; both driven by one shared `initStateMachineDemo(Reveal, idSuffix, numStates)` JS in the trailing `<script>`.
- **Concept:** a horizontal chain of numbered state circles connected by curved SVG arcs (plus a return arc looping the last node back to the first), driven by a Start button and a Step button. When the buttons appear, the whole diagram dims except the next relevant trigger arc/label. Pressing the right button "draws" that arc's path from tail to arrowhead, then lights up the destination state and shifts the highlight to the following trigger, so exactly one state and one upcoming trigger are ever highlighted at a time.
- **Mechanism:** `path.getTotalLength()` + `stroke-dasharray`/`stroke-dashoffset` animated via a forced-reflow + CSS transition (the classic SVG "line draw" technique), with the arrowhead `<marker>` opacity held at 0 until the draw finishes so it doesn't appear to float ahead of the line; a `currentArc`/`DEST[]` lookup table drives a `chain-dimmed` container class plus `.active`/`.highlight` toggles on nodes and arcs. Demo state activates/deactivates via `Reveal.on('fragmentshown'/'fragmenthidden', ...)` scoped to the specific buttons fragment (not just `slidechanged`), so stepping backward past that fragment cleanly un-dims everything.
- **Parametrized for reuse within the same deck:** the function takes an `idSuffix` (so two instances can coexist on different slides without id collisions — `'-4'` vs `''`) and `numStates` (drives `DEST[]` generation and every loop bound that used to be hardcoded to the state count). The loop-back arc's cubic-Bézier path is recomputed per instance by keeping the same endpoint-to-control-point offset (±92,92, which is what actually produces the ~45° corner-touching tangent) rather than linearly scaling the original path string, so the geometry stays correct at any width.
- **Reuse:** the dasharray/dashoffset draw-in plus marker-delay trick generalizes to "animate any SVG path drawing itself" (wiring diagrams, flowcharts, causal chains); the dim-all-but-the-next-highlighted-element pattern generalizes to any guided step-through of a diagram; the `idSuffix`/count-parametrization approach generalizes to any deck that wants "the same interactive diagram at two different scales" without duplicating the JS.

### Interactive hotspots on a redrawn schematic symbol
- **Where:** `Decks/AR2/StateMachines/State_Machines_Intro.html` (`#rs-latch-demo` ~line 425, `initRsLatchDemo` JS in the trailing `<script>`)
- **Concept:** a real piece of other software's iconography — here, FluidSim's RS latch block symbol — is redrawn as a small inline SVG (box + two input wire stubs + one output wire stub), then gets small live controls (Set/Reset buttons, a Q output light) positioned exactly at the wire endpoints, plus short colored connector lines bridging each control to the drawing. Pressing Set lights the output; pressing Reset clears it.
- **Mechanism:** started from a screenshot of the real symbol; its pixel geometry (wire endpoint coordinates, box edges) was measured once with a throwaway PIL script, converted to fractions of the image's width/height, then rebuilt as an SVG `viewBox` sized to match those same fractions 1:1 — so the original overlay math (fixed-px `position:absolute` offsets for the buttons/light) kept working unchanged when the raster image was swapped for the vector redraw. The SVG itself uses `stroke="var(--text)"` rather than the deck's accent green, deliberately reading as neutral/monochrome so it looks like "real software output" rather than one of the deck's own color-coded pedagogical diagrams. No fragment-gating or animation; just click handlers toggling a `.on` class on a small indicator, reset on `Reveal.on('slidechanged', ...)`.
- **Reuse:** generalizes to recreating any simple external-software icon/symbol as a crisp, theme-colorable SVG and wiring interactive callouts to its connection points; the "measure a reference image once, rebuild as SVG at the same viewBox fractions" trick keeps overlay coordinates stable across that swap.
- **Simplified variant:** `#s1-latch-demo` (~line 570, `initS1LatchDemo`) reuses the same button/light/`.rs-light` mechanism for a *hand-drawn* (not traced-from-a-reference) box, so there's no separate raster image to align against. It sidesteps the earlier connector-bar alignment bug entirely: rather than a colored `<div>` connector bar positioned independently next to the SVG wire (two elements whose centers have to be hand-computed to match), the SVG wire's endpoint coordinate *is* the button/light's `left`/`top` anchor, so they're mathematically the same point rather than two numbers that have to be kept in sync by hand.

### Data-driven relay circuit simulator (toggle switch or momentary NC push button)
- **Where:** `Decks/AR2/ACCircuits/EX4_AC_Relays_and_Contactors.html`, two instances sharing one `initRelaySims(Reveal)` engine in the trailing `<script>`: slide 5 (`data-input="toggle"`, a toggle switch driving relay coil CR and an NO contact feeding one lamp, based on Figure 58) and slide 14 (`data-input="nc-push"`, an NC push button driving CR with lamp A in series with an NO-contact lamp B branch and an NC-contact lamp C branch, Figure 65).
- **Concept:** a ladder-style schematic redrawn as inline SVG. Clicking the switch, or holding the push button, energizes or de-energizes the coil. Wires carrying current glow (green for the control circuit, cyan for the load circuit) and show dashes sloshing back and forth to suggest alternating current. Contacts show a cyan "conducting" bridge between their plates, lamps glow amber, and a row of state chips (Switch / Coil / Contact / Light) spells out the result in words.
- **Mechanism:** no per-circuit JS. The engine derives one boolean (`closed`, from `actuated` and the input type) and exposes `energized / deenergized / always / closed / actuated` conditions; every element carrying `data-when="<condition>"` gets `.on` toggled, and chips with `data-on`/`data-off` swap their innerHTML. Each `path.w` wire is cloned once at init into a `.flow` overlay with a dash pattern and an `alternate` dashoffset animation (disabled under `prefers-reduced-motion`). The toggle blade and the push-button bar animate with CSS transforms using `transform-box: view-box` and an inline `transform-origin` at the pivot. The hold control uses `pointerdown` / `pointerup` / `pointerleave` / `pointercancel`, deliberately without `setPointerCapture`. Storyboard clones are skipped with `root.closest('#storyboard')`, and every instance resets to un-actuated on `slidechanged`.
- **Reuse:** draw any relay or contactor ladder diagram (seal-in / start-stop latch, interlocks, multiple contacts on one coil) and tag each wire, contact bridge, coil, and lamp with the condition it depends on, with no JS changes. To add a seal-in latch, extend `render()` so `closed` also depends on a held state of its own.
- **Also used in:** `Decks/AR2/Silicon in Control/Day1_Evolution_of_Control.html` slide 3, a DC variant: a 24 V battery symbol, current dashes that travel one way (`dc-flow`, linear) instead of sloshing, and an Operations counter chip that counts each closing of the switch, for a discussion of relay wear.

### Overcurrent protection simulator (fuse blows / breaker trips, replace or reset)
- **Where:** `Decks/AR2/ACCircuits/EX5_Electrical_Distribution.html`, slide 13 (`.prot-sim`, `initProtectionSims(Reveal)` in the trailing `<script>`). Adapted from the EX4 relay simulator above.
- **Concept:** an ac source feeds a lamp through a protection device, with a fault switch wired across the lamp. A segmented control picks the device (fuse or circuit breaker). Closing the fault switch shorts the lamp: the live wires flash red with fast-moving dashes and a red halo appears around the device for a brief "overcurrent" surge, then the fuse element breaks (blown) or the breaker arc swings open (tripped). A green restore button ("Replace the fuse" / "Reset the breaker") appears only while the device is open; restoring while the fault is still closed immediately surges and opens again, teaching "remove the cause before resetting." Chips report device state, lamp state, and a running count of fuses used versus times reset, which makes the fuse's single-use cost and the breaker's longer service life visible.
- **Mechanism:** same `data-when` engine as the relay simulator, with a richer state object (`device`, `fault`, `open`, `surging`, counters) mapped to conditions `live / lamp / faultflow / faultclosed / fuse / breaker / intact / blown / tripped / open / surging`. Elements with class `.cond-show` are `display:none` unless `.on`, which swaps whole symbol groups (fuse vs. breaker drawing, blown vs. intact element) and hides the restore button. The surge is a single `setTimeout` (700 ms) that flips `surging` off and `open` on; the root gets a `.surging` class so the CSS recolors every currently-`.on` wire red and speeds up the `.flow` dash animation. The breaker arm uses `transform-box: view-box` with an inline `transform-origin` at its left terminal. Storyboard clones are skipped with `root.closest('#storyboard')`, and the sim resets to an intact fuse on `slidechanged`.
- **Reuse:** any "protective device opens the circuit under a fault" moment: GFCI trips on a ground fault, overload relays, thermal cutouts, or polyfuses that self-reset after cooling (swap the restore action for a timer). Add more fault types (overload vs. short) by adding conditions and wires tagged with them.

### Hidden-fault troubleshooting simulator (voltmeter and ohmmeter methods)
- **Where:** `Decks/AR2/ACCircuits/EX6_Troubleshooting_Methods.html`, slide 11 (`.fault-sim`, `initFaultFinders(Reveal)` in the trailing `<script>`). Based on Figures 82 and 83.
- **Concept:** a 24 V ac source feeds four identical 60 Ω lights in series, with one random hidden fault: a light that is open, shorted (0.1 to 0.3 Ω), reading too high (80 to 180 Ω), or reading too low (15 to 45 Ω), or a dead source. Fault types are dealt from a shuffled bag, so every five faults include each type once (including the dead source) and a type never repeats back to back, and high/low values are re-rolled each time so students cannot memorize one number. A too-high light glows brighter while the rest dim; a too-low light dims while the rest brighten. In voltmeter mode the source is on, the lights glow in proportion to the power they actually receive (so the "observation" step is real: an open leaves everything dark, a short darkens one light and brightens the rest), and clicking probe positions 1 to 4 draws a dashed lead from the meter and reads the voltage to the source's negative terminal. Ohmmeter mode removes the source (drawn as two open terminals) and shows one Ω meter across each light, as in Figure 83. Every reading is logged next to its expected value, the student names the faulty component, and a correct answer outlines the bad light in red and explains the symptoms. A counter tracks how many measurements were needed.
- **Mechanism:** readings are computed from a real circuit model, not a lookup table: `resistances()` builds the series string with the fault applied, `positionVolts(k)` handles the open case (source voltage up to the open, 0 V after it) and otherwise uses the voltage-divider formula, and `relativePower(k)` drives a per-lamp `--g` CSS variable used for `fill-opacity` and a blurred glow. Guard the open case before computing power: `0 * Infinity` is `NaN`, and a `NaN` custom property falls back to full opacity, so a burned-out light would glow. `.only-volt` / `.only-ohm` swap the drawing and controls under a root `.mode-ohm` class. ### Draggable node-graph builder ("Draw It" network activity)
- **Where:** `Decks/CSP/Unit 2 - The Internet/2.2 - Building a Network/2.2-building-a-network.html` (`.netbuild` markup, four instances `#netbuild-1`..`#netbuild-4` on slides 5/7/9/11; `initNetworkBuilder` JS inside `afterInit`)
- **Concept:** a small set of labeled SVG nodes arranged on a circle; students drag from one node to another to add a connection (a slightly bowed quadratic-bezier curve rather than a straight chord, so overlapping connections stay visually distinguishable), and click an existing line to remove just that one. Dragging the same pair again adds a second, redundant parallel line instead of removing the first — parallel lines between the same pair fan out sideways so multiple backup connections stay individually visible and clickable rather than stacking exactly on top of each other. A stats bar tracks total connection count and whole-graph connectivity. Two optional tools escalate with the lesson's guidelines: "Test a Cut" lets a student click one strand of a connection to simulate severing just that physical line (a redundant pair survives a single cut) and flags any node that becomes fully unreachable in red; "Find a Path" lets a student tap two nodes to highlight the shortest remaining route between them and reports the hop count.
- **Mechanism:** node positions are computed from a labels array on a circle (`cx + r*cos/sin`), not hardcoded, so the node count is parametrizable. Edges are stored as a per-pair *count* (`edges["A-B"] = 2`) rather than a boolean, with a parallel per-pair cut *count* (`cuts["A-B"]`) capped at the edge count; connectivity BFS treats a pair as traversable only while `edges[k] - cuts[k] > 0`. Rendering draws `count` separate paths per pair, each offset sideways from the shared outward bow by `(index - (count-1)/2) * spread` so 1, 2, or 3 parallel strands read as distinct fanned lines instead of one thick overlap; clicking a specific rendered strand reads *that strand's own* cut/active state (by its render index against the pair's cut count) to decide whether the click cuts one more or restores one, so the interaction reads as "click a red strand to restore it, click a live strand to cut it" even though strands aren't independently tracked once cut/uncut. Dragging is implemented with plain `pointerdown`/`pointermove`/`pointerup` listeners on the SVG root — deliberately *not* `setPointerCapture` — because capturing the pointer caused Chromium to occasionally fire a spurious `pointercancel` when a new drag started from the node that had just been the previous drag's drop target; listening on `window` for move/up sidesteps that capture-lifecycle quirk. A single pointer gesture does double duty: dragging fully from node A to node B commits an edge directly, while a plain tap (down+up on the same node with no distinct second node) arms it as a "selected" node so a following tap on a second node connects them too — giving touch/keyboard users a click-click fallback without a separate code path. Each of the widget's DOM lookups goes through a `getLiveElementById` helper (`querySelectorAll('#id')` filtered to exclude anything under `#storyboard`) since SyncDeck's storyboard strip clones slide markup including duplicate ids, so a plain `document.getElementById` risks returning the inert clone. **Bug worth remembering:** conditionally toggling a class via `classList.toggle(name, someExpression)` is only safe if `someExpression` is coerced to a real boolean first (`!!(...)`) — passing a value that evaluates to `undefined` (e.g. an `&&` chain that starts with a falsy-but-not-boolean guard) makes `classList.toggle` perform a genuine toggle instead of forcing the state, which desyncs the visual state from the data model on every re-render.
- **Reuse:** the node-on-a-circle + drag-to-add/click-to-remove mechanism generalizes to any "build a graph" activity (network topology, state-machine wiring, relationship mapping); the count-per-pair model generalizes to any activity that wants to teach redundancy through literal parallel/backup connections rather than just presence-or-absence edges; the cut-simulation and shortest-path tools generalize to any lesson that wants students to reason about redundancy or path length over a graph they built themselves, not a pre-made one.
- **Also worth remembering:** resonance/postboard question `text` is the *only* thing students see once the activity overlay launches — the surrounding slide's prose (background context, setup) is hidden behind it. Any context the question depends on (e.g. "recall X from last lesson...") has to be restated inline in the question `text` itself, not left to the slide's own paragraph.

### Head to Head (open loop stepper vs. speed control vs. servo, raced in lockstep)
- **Where:** same file, slide 16 (`.hh`, `buildHeadToHead(root)`), after the challenge slide (14) and a Resonance prediction slide (15).
- **Concept:** three arm joints race side by side on one command (target, speed), one load (light, medium, heavy, overloaded), and one optional shared bump. Each arm has a panel with its dial (solid arm in the system's color, dashed commanded line, amber target) and five fixed lines: off-target error (✓/✗ within 1° after the run), the feedback that system really has (none, speed, encoder angle), a system line (stepper lost steps, brushless "position unknown", servo drive % / LIMIT / FAULT), settle time, and the prediction. Students check the arms they expect to end within 1°, then **Lock prediction**; Run unlocks only after a lock, and changing the command clears the lock. One shared position-vs-time graph shows the dashed command and three actual traces, each with its own color and line thickness (12, 7, 3 units, drawn thickest first so overlapping traces show as nested stripes) and a letter label at its end; the labels are spread at least 30 units apart, centered on the line ends. The angle axis scales to the target (−10% to +120%) so a few degrees of miss stays visible. The run report counts right predictions and names the key failure (the stepper's controller still believing the commanded angle, a servo fault, or brushless speed-not-position drift).
- **Mechanism:** torque in units of motor rating; each arm obeys `a'' = (motor − friction − bump) / J × 1200` with stiction, integrated in 10 substeps per frame from one trapezoidal command profile (600°/s²). Stepper: follows the command in 1.8° steps unless friction plus acceleration torque exceeds a pull-out torque that falls with speed; it then slips, the loss rounds to whole rotor teeth (4 steps) and is capped at steps sent, and the controller still reports the commanded angle; a bump costs 4 steps. Brushless: a PI speed loop runs for the computed time, then brakes, with no position loop. Servo: a torque-limited PID on the encoder angle with anti-windup (the integral only builds below the torque limit, so a bump never leaves it parked past the target), raising a following-error fault after 1.5 s saturated more than 20° off. A run is the move, then (Bump on) a 0.3 s knock on all three 1 s after arrival; it ends when every arm has been still for 0.6 s after the last event, where a servo more than 1° off counts as still moving, or after 5 s. Friction only stops a moving arm (zeroing velocity on a sign flip from rest blocked breakaway; check for that bug in any reuse).
- **Reuse:** any open-loop vs. closed-loop comparison run as a prediction race (heater with timer vs. thermostat, cruise control, line following): per-system state objects stepped in lockstep from shared inputs.

The wires turn cyan and the LED glows only while current flows. A measurement log keeps the last three readings with the orientation, so students can copy evidence into their notebooks.
- **Mechanism:** forward drops V_LED = 1.85 V and V_D = 0.62 V give I = (5 − 1.85 − 0.62) / 1 kΩ = 2.53 mA when both conduct; if exactly one device is reversed, I = 0 and that device has the full 5 V across it; if both are reversed the reading is shown as unsteady (leakage decides the split) with a caution message. Orientation is named by where the band points (A toward the negative side, B toward the positive side) so the widget never says "forward" or "reverse" before students have made a claim.
- **Reuse:** any "what is this unknown component" bench: swap the mystery part's model (a resistor, a capacitor charging, a Zener at a higher supply) and keep the loop, probe marks, DMM, and log.

### Doping Lab (silicon lattice with electrons, holes, dopants, and a PN junction)
- **Where:** shared unit script `Decks/AR2/Silicon in Control/semiconductor-sims.js` (`SiliconSims.buildDopingLab(root)`, styles in that folder's `theme.css`). Used on `Day2_What_Makes_a_Semiconductor.html` slide 9 (all modes) and `Day3_Diodes_and_Biasing.html` slide 5 (`data-mode="junction"`: PN junction only, with a bias slider from −3 to +1 V).
- **Concept:** a 14 × 6 lattice of silicon atoms between two metal contacts. Modes: Pure Si, N-type, P-type, and PN junction. Free electrons are blue dots that random-walk and drift; holes are pink rings that move only by hopping from bond to bond, and each hop draws a short blue streak for the electron that filled it (the "a hole is a missing electron" misconception target). Dopants show their fixed ion charge (P⁺, B⁻); students add or remove them with a slider or by clicking atoms. A temperature slider generates electron-hole pairs (a flash marks each pair) at a rate that doubles about every 12 °C. In junction mode, carriers near the boundary first cross and recombine, then a dashed depletion band forms whose exposed ions glow; forward bias shrinks the band until carriers flood across, reverse bias widens it, and heating under reverse bias shows the leakage current. Tiles count electrons, holes, and current (carriers per second through the contacts or across the junction), and a fixed-height feedback line explains the state.
- **Mechanism:** uniform modes use periodic contacts (a carrier leaving one contact re-enters at the other and counts toward the current) with drift from the applied voltage. Junction mode: barrier φ = max(0.03, 0.7 − V), depletion half-width d = 55·√(φ/0.7); inside the band electrons are pushed toward N and holes toward P with strength ∝ √(φ/0.7); above 0.35 V carriers also drift toward the junction. A 2.5 s formation phase draws carriers near the boundary across so they recombine before the field turns on. Current counts each carrier's **first** crossing only (counting every crossing let carriers jittering at the boundary create charge); a carrier that crossed becomes a minority carrier with a ~0.5–1.1 s lifetime and then recombines with the nearest majority carrier. A `neutralize()` step feeds or absorbs majority carriers at the contacts so each side holds one per dopant outside the band plus one per minority carrier on that side; event-by-event replacement drifted out of balance. Measured with the default dopants: 0 /s at 0.3 V, about 1 /s at 0.6 V, 3 to 4 /s at 0.7 to 1.0 V, 0 at reverse bias and 25 °C, and about −7 /s at −3 V and 150 °C. Freshly generated pairs cannot recombine for 0.6 s so students can see them.
- **Pacing controls:** the lab starts in Slow (0.35× time) with a Slow / Normal toggle (`[data-speed]`) and a Pause button (`[data-act="pause"]`), because at full speed students could not follow individual carriers. Clicking a carrier follows it: an amber outline plus a dotted trail of its last 40 positions (reset when it wraps through a contact), and the feedback line explains what it is doing, or says it recombined. The battery value carries across mode switches, clamped to the new range (junction mode is −3 to +1 V); only leaving the slide resets it to 0.
- **Reuse:** any carrier-level picture: transistor base (NPN as two junctions), LEDs (recombination flashes as light), photodiodes (generation by light instead of heat). Change the dopant layout and the force rules.

### Diode Bench (adjustable supply, Shockley diode, DMM, and I–V plot)
- **Where:** same shared script (`SiliconSims.buildDiodeBench(root)`), used on `Day3_Diodes_and_Biasing.html` slide 11, the virtual version of the Day 3 bench lab and its I–V extension.

### Rectifier Lab (half-wave and bridge, filter capacitor, scope with a sweeping cursor)
- **Where:** shared unit script `Decks/AR2/Silicon in Control/semiconductor-sims.js` (`SiliconSims.buildRectifierLab(root)`), used on `Day4_Rectifiers_and_Protection.html` slide 6, with its tasks on slide 7.
- **Concept:** a 12 VAC source (17.0 V peak) feeds a half-wave rectifier (D1) or a four-diode bridge, a 1 kΩ load, and an optional filter capacitor (none, 100, 470, 1000 µF). A two-channel scope shows two cycles of input (dashed amber) and output (cyan). A cursor sweeps the scope in slow motion, and the circuit lights the diodes and wires carrying current at that instant: D1 for half-wave, D1 and D3 then D2 and D4 for the bridge, and the capacitor-to-load loop in amber while the diodes are off. - **Mechanism:** steady state found by stepping 12 cycles at 400 steps per cycle and keeping the last two.
