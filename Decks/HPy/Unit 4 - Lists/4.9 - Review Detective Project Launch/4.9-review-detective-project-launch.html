The Project

Can a program help us understand reviews?

Your team will build Review Detective, a console program that reads consumer reviews and reports on the language in them: how positive or negative it sounds, which words it leans on, and where its signals conflict.

Driving question: Can a program help us understand consumer reviews, and when might its conclusions be misleading?

The second half of that question matters as much as the first. A finished project reports what the program found and where its analysis falls short.

Honest Claims

What the program can and cannot tell us

Review Detective can count, compare, and describe language. It can show that one review uses twice as many negative words as another, or repeats one adjective eight times, and point to the exact words.
Review Detective cannot prove that a review is fake, or that a sentiment score is the truth about a product. Word counts miss sarcasm, negation, and context. Your report should say so.
The Shared Data

One review per line

Every team gets the same sample_reviews.txt, with one review per line. splitlines turns the file into a list of reviews, and split turns each review into a list of words.

Everything after that is list processing, and every module receives its words in the same agreed format: a list of lowercase words with punctuation removed.

main.py
text = open("sample_reviews.txt").read()
reviews = text.splitlines()

for review in reviews:
    words = cleanWords(review)
    # words is a list like:
    # ['great', 'fan', 'but', 'loud']
    ...
cleanWords (lowercase, strip punctuation, split) can be provided in the starter files so no student's role is mostly input handling. Reading a file with open() is new; it is the only file I/O students need.

Individual Expectations

Your module must show that you can…

  • create lists and fill them, and traverse lists with loops;
  • search, count, or filter values with conditions;
  • build a new list by transforming or selecting values from another list;
  • perform one intentional, documented list mutation, and explain why it belongs there;
  • define and test several functions that take lists as arguments or return them;
  • explain a trace of your own code, including any aliases.

Your grade comes from your code, your tests, your traces, and your explanations. It does not come from how many commits you make.

Contracts Before Code

Agree on the interface first

Before anyone writes a loop, the team agrees on every shared function's name, parameters, return value, and whether it mutates its inputs.

Then main.py can depend on what each function promises, not on how it is written. You can test your module against the shared sample inputs without waiting for anyone.

sentiment.py
def countPositive(words, positiveWords):
    # Returns the number of words in words
    # that appear in positiveWords.
    # Does not change either list.
    ...

def sentimentScore(words, positiveWords,
                   negativeWords):
    # Returns positives minus negatives.
    # Does not change any list.
    ...
Checkpoint · Contracts

Which is a complete contract for topWords(words, n)?

  • AReturns a new list of the n most common words, most common first. Does not change words.
  • BFinds the top words using a loop and a list of counts.
  • CSorts words and returns the first n.
  • DReturns a list.
B describes how, not what. C describes a mutating implementation and leaves out what "top" means. D is too vague to test. A says what is returned, in what order, and what happens to the input, so a teammate can write a test from it.
Independent Modules

Stubs, imports, and test files

A stub is a function that keeps its contract's shape but returns a placeholder. With stubs in place, main.py runs from day one.

import lets one file use another file's functions. Keep each module's tests in its own test file, which imports the module and runs the tests. That way, importing the module into main.py never runs your tests.

test_language.py
from language import topWords

def testTopWords():
    words = ["so", "loud", "so"]
    assert(topWords(words, 1) == ["so"])
    assert(words == ["so", "loud", "so"])

The Repository

One repository, clear owners

Each team shares one GitHub repository. Every file has an owner, and you only edit files you own.

Shared files, like main.py and README.md, need a team rule. For example, one person owns main.py, and everyone else asks them for changes.

Version Control

Pull, edit and test, commit, push

Git keeps every saved version of the project, and GitHub shares it with your team. You will use the Source Control view in VS Code for one simple cycle, every time you sit down to work.

1. Pull

Download your teammates' latest commits before you start, so you build on the newest version.

2. Edit and test

Change only your own files. Run your test file until it passes.

3. Commit

Save a snapshot with a message that says what changed and why, like topWords handles ties.

4. Push

Upload your commits to GitHub. The Sync Changes button pulls and then pushes.

When a Push Is Rejected

Someone pushed first

If a teammate pushed after your last pull, GitHub rejects your push, because your copy is missing their work. That is normal, not an error in your code.

Pull to bring their commits into your copy, run your tests again, then push. Because each of you edits separate files, Git can usually combine the work on its own. Two people editing the same file at the same time is what causes a merge conflict, which is why ownership matters.

Checkpoint · GitHub

Your push was rejected. What do you do?

  • ADelete your copy of the repository and clone it again
  • BCopy your teammate's files into yours by hand
  • CPull, run your tests again, then push
  • DKeep working and never push until the project is done
Team Design Activity

Write the contracts together

  • Choose your modules. Each teammate drafts the contracts for three functions in their module: name, parameters, return value, and mutation.
  • For each function, write one test input from sample_reviews.txt and the exact result you expect, worked out by hand.
  • Trade drafts. Your teammates check that each contract is complete enough to write a test from, and that main.py can call it.
  • Record the agreed contracts in README.md. That is your team's first commit.
VS Code · Collaborative Project

First work session

  1. Clone your team's repository and open it in VS Code.
  2. Write stubs for all three of your functions, so main.py can call them.
  3. Write your test file from the contracts, and watch the tests fail against the stubs.
  4. Replace one stub with a real implementation until its tests pass. Then pull, commit, and push.
