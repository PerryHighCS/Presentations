4.10 Testing and Interpreting Results

tracing complex list code · edge cases · correct code versus trustworthy conclusions

The Question

Can we trust the results?

Before Review Detective's report means anything, two different questions need answers.

Is the code correct? Does each function do exactly what its contract says, on every input, including the strange ones? Tracing and testing answer this.
Is the conclusion valid? Even if every function is perfect, does the number it produces mean what the report claims? Only careful interpretation answers this.
4.2.13 Code Tracing with Lists

Predict, trace, run, explain

Lists are the first mutable data we have traced, so these traces can be hard. Use the same protocol every time, and keep scratch paper out.

  • Predict: read the whole program and guess the output before tracing.
  • Trace: draw frames, variables, and list objects as boxes and arrows, one line at a time.
  • Run: check your trace against the real output.
  • Explain: for any line you got wrong, name the exact step where your drawing went wrong.

main.py
def ct(L):
    M = [v*10 for v in L]
    N1 = [x**2 for x in L if x > L[0]]
    L = sorted(L)
    N2 = [x**2 for x in L if x > L[0]]
    print(L + M)
    return N1 + N2 + [max(L)] * (1 + min(L))
L = [4, 1, 6]
print(ct(L))
print(L)
The key line is L = sorted(L). It builds a new sorted list and moves only the local L's arrow, so the caller's list stays [4, 1, 6]. N1 uses the original order (only 6 > 4), N2 the sorted one (4 and 6 > 1). [max(L)] * (1 + min(L)) is [6] * 2.
Trace 2 · Explain

The line that decides everything

L = sorted(L) builds a new, sorted list and points the local L at it. The caller's list is never mutated, so the last line prints [4, 1, 6].

Lines 3 and 5 are the same comprehension, but they run on different lists. N1 filters the original order, where L[0] is 4, and keeps only 6. N2 filters the sorted list, where L[0] is 1, and keeps 4 and 6.

If line 4 had been L.sort(), the caller's list would have been sorted too, and the last line would print [1, 4, 6]. One line, two very different programs.

Trace 3 · Predict

Two lines of output

  • A[5, 9, 4, 5, 4] / [5, 9, 4, 5, 4]
  • B[9, 5, 4, 5, 4] / None
  • C[5, 9, 4, 5, 4] / None
  • D[5, 4, 5, 4] / 9
main.py
def ct(L):
    M = []
    while sum(L) > sum(M):
        M.extend(L[:2])
    v = M.pop(0)
    v += M.pop()
    M.insert(1, v)
    print(M)
print(ct(list(range(4, 8))))
L is [4, 5, 6, 7], sum 22. M grows [4, 5], then [4, 5, 4, 5], then [4, 5, 4, 5, 4, 5] with sum 27, and the loop stops. pop(0) gives 4, pop() gives 5, so v is 9, inserted at index 1. ct has no return statement, so the outer print shows None.

Add at least one test of each kind to every module before integration.

Correct Is Not the Same as Valid

A perfect count can still mislead

A sentiment counter can count every positive and negative word exactly right and still reach the wrong conclusion about a review.

  • Negation: "not good" counts as one positive word.
  • Sarcasm: "Great, it broke on day two" counts great as praise.
  • Repetition: one enthusiastic reviewer who types "love love love" outweighs a careful one.
  • Context: "cheap" is good news for a price and bad news for a hinge.

VS Code · Integration and Investigation

Finish, combine, and investigate

  1. Finish your module. Every function passes its tests, including the edge cases and the input-unchanged checks.
  2. Pull, integrate through main.py, and run the full program on the sample reviews.
  3. Run two contrasting reviews, then edit one on purpose and run it again. Record what changed.
  4. In README.md, document one case your analysis handles well and one where its interpretation is limited.
Presenting Your Module

What to show

  • One function you wrote: its contract, and whether it mutates anything and why.
  • A test that checks an edge case, and the input after the call.
  • A trace of one call, drawn as boxes and arrows, including any aliases.
  • A limitation: an input where your function is correct but the conclusion would mislead.
