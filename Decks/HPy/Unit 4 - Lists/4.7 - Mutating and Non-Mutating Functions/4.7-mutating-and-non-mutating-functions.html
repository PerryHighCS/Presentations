4.7 Mutating and Non-Mutating Functions

The Question

The answer was right. So what went wrong?

A teammate's median function returns the correct median. But after you call it, your list of star ratings is in a different order than before.

Nothing in the call median(stars) says "and also rearrange my list." The function broke a promise its caller assumed it would keep.

main.py
def median(L):
    L.sort()
    return L[len(L) // 2]

stars = [5, 1, 4]
print(median(stars))   # 4
print(stars)           # [1, 4, 5] ?!

4.2.12 Writing Functions

Functions must be non-mutating by default

When you write a function that takes a list, you decide whether it may change that list. The default answer is no. A caller who asks for a median, a count, or a list of long words does not expect their data to change.

A function should be mutating only when changing the list is clearly its job, like removeAll(L, v) or L.sort(). Then its name and its comment must say so.

Python's naming pattern helps. A command verb like sort or removeAll suggests a change. A past-tense or noun name like sorted or longWords suggests a new result. Use the same pattern for your own functions.
Mutating and Non-Mutating removeAll

Same job, two promises, two ways to call

mutating
# Mutates L: removes every v.
# Returns None.
def removeAll(L, v):
    i = 0
    while i < len(L):
        if L[i] == v:
            L.pop(i)
        else:
            i += 1

removeAll(L, 2)
non-mutating
# Returns a new list without v.
# Does not change L.
def removeAll(L, v):
    result = []
    for value in L:
        if value != v:
            result.append(value)
    return result

M = removeAll(L, 2)

The mutating version is called on a line by itself, because it returns None. The non-mutating version's result must be stored, or it is lost.

A Common Question

Can a non-mutating function call append?

Yes. The non-mutating removeAll calls result.append(value), a mutating method. That is fine, because result is a local list the function created. Nobody outside the function has an arrow to it until it is returned.

Non-mutating means one thing: the function does not change its parameters. It may build, change, sort, and pop its own local lists as much as it likes. A safe way to fix median is to sort a local copy:

main.py
def median(L):
    M = copy.copy(L)
    M.sort()            # changes M, not L
    return M[len(M) // 2]
Checkpoint · Function Promises

Which statement is false?

  • AUnless we specifically say a function is mutating, it must be non-mutating.
  • BAll mutating functions return None because they directly change their parameters.
  • CA non-mutating function may create new local lists and mutate those.
  • DWhen you write a function that takes a list, you must decide whether it is allowed to change the list.
B is false: mutating functions generally return None, but L.pop() is mutating and returns the removed value. A function can both mutate and return something useful, as long as its contract says so.
Contracts

Say it, then test it

Start every list function with a comment that states its contract: what it returns, and whether it changes its arguments.

Then test both halves of the promise. Check the return value, and check the argument after the call: unchanged for a non-mutating function, changed in exactly the promised way for a mutating one.

main.py
def testMedian():
    stars = [5, 1, 4]
    assert(median(stars) == 4)
    assert(stars == [5, 1, 4])

def testRemoveAll():
    L = [2, 1, 2, 2]
    assert(removeAll(L, 2) == None)
    assert(L == [1])
Find the Broken Promises

Two functions change what they should only read

Each function promises not to change its argument, and the tests check both the return value and the argument afterward. Run the tests, use the failing assert to find the first broken promise, fix it, and repeat. Your fixes must not change what any function returns.

Investigation · Briefing

Who changed the list?

A team of programmers runs four analysis functions on one shared list of words from a review. Someone's function quietly changes that list, so the report at the end is wrong. Your job is to find out whose, using as little time as you can.

  • Read the case file: the bug report, the expected output, and the team's commit log.
  • Spend your 12 minutes on tests. Each test returns real evidence, but not every test helps.
  • Strike out the suspects your evidence rules out, then name the culprit and a fix, and tag the readings that prove it.

Some choices are bad practice. They cost time and go on your record.
