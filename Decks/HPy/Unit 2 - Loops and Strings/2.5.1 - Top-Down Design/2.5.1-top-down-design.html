2.5.1 Top-Down Design

Some problems are too complicated for one function

We often run into problems that are too complicated to solve inside a single function. It helps to break the problem apart using multiple helper functions, one for each sub-problem. We call this top-down design: start from the big picture, and work your way down into smaller pieces.

The Process

Write the main idea first

  • Start writing an algorithm for the main problem, in plain steps.
  • When you hit a part that feels complicated, give it a well-named helper function instead of writing it out right there.
  • Assume the helper is already written and correct, then keep going with the main problem. Come back and actually write the helper later.
  • Repeat this for every complicated part, until the main problem is done and every helper is written.
The key move is assuming. You don't need isHappy(n) to exist yet to write code that calls isHappy(n). Trust the name, keep moving, and fill it in afterward.
Why Bother

Three benefits of top-down design

Cleaner code
One short function that calls well-named helpers reads far easier than one long function with everything tangled together.
Reusable logic
A helper you write for one problem can be reused, unchanged, in a completely different problem later.
Easier testing
You can test each helper on its own, so a bug points you straight at which small function is wrong.

Debugging five short, individually-tested functions is almost always easier than debugging one giant one.

Asserts are your guide

Test-Driven Development

Test-driven development (TDD) is a programming workflow that flips the usual order of writing code and testing it. Instead of writing the code first and testing it afterward, you write the tests first, then write the code to make them pass.

A Failing Test Is a To-Do List

Stub it, test it, then build it

Here's what that looks like in practice. Follow these four steps for every function you write.

  1. 1Write the function header with an obviously-wrong placeholder body, like return 42, so the file runs without crashing.
  2. 2Write the assert test cases for it right away, based only on what the function is supposed to do.
  3. 3Run it. Every assert that fails is telling you exactly what's still broken, that's your to-do list.
  4. 4Edit the real function until every assert passes silently.
main.py
def isHappy(n):
    return 42  # obviously wrong, on purpose

def testIsHappy():
    assert(isHappy(1) == True)
    assert(isHappy(28) == True)
    assert(isHappy(2) == False)
    print("Works!")
Guided Exercise · Happy Numbers

Let's build nthHappyPrime(n) together

We'll walk through top-down design as a class, using one example problem from start to finish. Given a positive number n, compute a new number by summing the square of every digit of n. Repeat that process on the result, over and over.

Every number eventually lands on either 1 or 4, and then stays there forever. A number that reaches 1 is happy; a number that reaches 4 is unhappy.

The Goal

Write nthHappyPrime(n)

A happy prime is a number that is both happy and prime. 7 is the first one.

Write nthHappyPrime(n), which takes an integer n and returns the nth happy prime, counting from 0.

Design Top-Down, Build Bottom-Up

Sketch it top-down, write it bottom-up

Patterns in Development

Some code shapes show up again and again

A pattern is a recognizable shape of code that solves a certain kind of problem, independent of the problem-specific details filled into it. Once you recognize a pattern, you can sketch its skeleton immediately, before you've written a single line of the logic that's actually specific to your problem.

  • Accumulator: a variable that starts at an identity value and updates a little more on every pass, like the running total in sumToN.
  • Count-and-track-the-best: tally how often each value shows up, and remember the best one so far, like mostFrequentDigit.
  • Search for the nth match: choose candidate values, test each one, and count only the ones that qualify.
Example · A Pattern You Already Know

The nth X pattern

You've written this loop shape before: nthPrime. Whenever a problem asks for the nth thing with some property, the shape is the same.

Find candidate values one at a time, test each one, and only count the ones that qualify. Once you recognize the shape, you can sketch the outer loop before you've written a single helper.

The only thing that changes from one problem to the next is the property being tested. In nthPrime, the property is primality. In nthHappyPrime, the property is being both happy and prime.

the pattern
def nthX(n):
    candidate = STARTING_VALUE
    count = 0
    while True:
        candidate += 1
        if hasProperty(candidate):
            if count == n:
                return candidate
            count += 1

Recap

Top-down design and test-driven development

  • Top-down design: sketch the main problem first, hand off complicated parts to well-named helper functions, and assume each one works until you actually write it.
  • Recognize the pattern: many problems share a shape you've already coded, like "search for the nth match." Naming the pattern lets you sketch the skeleton before writing a single line of problem-specific logic.
  • Test-driven development: write the assert test cases before the real implementation. A failing test tells you exactly what's still broken.
  • Build order: design top-down, but build and test bottom-up, starting with the helper that has no dependencies.
  • Well-tested helpers are reusable. isPrime proved that today, and it won't be the last time.
